## Executive summary

- **Drag-to-reorder has a directional off-by-one bug**: dragging a token forward within a step, or a step forward in the list, lands the dragged item one slot past where it was dropped. Backward drags are correct. The project's own Playwright driver only exercises a backward step-drag, so this has never been caught. (`src/state/document.ts:121-146`, `:149-156`; `src/components/StepList/StepList.tsx:17-27`)
- Aside from that bug, the codebase is unusually well-disciplined for its size: consistent mutator patterns in `state/document.ts`, one source of truth per concern, thorough inline rationale comments, and documentation (`docs/Milestones.md`, `Fixed-Issues.md`, `Known-Issues.md`) that is honest about what's incomplete rather than aspirational.
- A handful of small, low-risk duplications exist (`descriptionFor` copy-pasted between `StepDetails.tsx` and `TokenDetails.tsx`; a `TokenCategory` value named `"note"` colliding in name, not meaning, with `InstructionToken.note`) — cosmetic, worth a quick cleanup but not urgent.
- `model/validate.ts`'s `validateDocument` and `model/migrate.ts`'s `migrate` are currently unused (no import sites) — both are explicitly-documented stubs for not-yet-started Phase 2 tasks (14, 19), so this reads as deliberate scaffolding rather than accidental dead code, but it's worth knowing they aren't wired to anything yet.
- No secrets, no scope violations, nothing needing a destructive fix — the project is genuinely early (Phase 2, tasks 5–12 of 24 done) and the architecture holds up fine for that size; nothing here suggests it's outgrowing its current structure.

## Findings

### Major

**1. Forward drag-reorder overshoots by one position (same bug in two places)**
- **File/lines**: `src/state/document.ts:121-146` (`moveToken`, same-step branch at 132-136) and `src/state/document.ts:149-156` (`reorderSteps`), driven by `src/components/StepList/StepList.tsx:17-27` (`resolveDropIndex`) and `src/lib/pointer-drag.ts:84-102` (`resolveTokenDropTarget`).
- **What I found**: Both reorder paths use the same pattern — hit-test the pointer against the *currently rendered* (pre-removal) list to get a target index, then `filter`/`splice` the dragged item out and reinsert it at that same numeric index. Because removing the dragged item shifts everything after its original position back by one, reinserting at the raw pre-removal index lands the item one slot **past** the intended drop point whenever the target is after the source. Dragging *backward* (target before source) is unaffected, because removal doesn't touch anything before the target index.
- **How I found it**: Traced the data flow for both `moveToken`'s same-step branch and `reorderSteps`, then worked through concrete before/after arrays by hand:
  - `moveToken`: tokens `[A,B,C]`, drag A onto C (`data-token-index=2`) → `withoutToken=[B,C]`, `insertToken([B,C], A, 2)` clamps to `2` → result `[B,C,A]` (A lands *after* C, not at/before it as dropped).
  - `reorderSteps`: same shape of bug via `resolveDropIndex`, which returns the index of the first item whose midpoint is below the cursor (pre-removal array) and is passed straight into `steps.splice(fromIndex,1)` / `steps.splice(clamped,0,moved)` with no adjustment for the shift.
  - Cross-checked against `.claude/skills/run-instruction-builder/driver.mjs:217-230`: the only automated reorder test drags step 2 **above** step 1 (a backward move), which is exactly the direction that doesn't trigger the bug. The token-move test (`driver.mjs:200-214`) moves a token *between* steps (independent arrays, no shift issue), never reorders within one step. So the forward-drag path is untested end to end.
- **Consequence**: Any user dragging a step down the list, or a token later within the same step's row, ends up with the item one position further than where they released it — a visible, repeatable ordering bug in the app's core interaction (drag-and-drop, task 9), currently invisible to both manual spot-checks (if only backward drags were tried) and the existing regression driver.
- **Severity**: Major. **Category**: Correctness. **Confidence**: Medium-High (fully reasoned through with concrete before/after traces on the actual code; not yet confirmed by driving the real UI).
- **Suggested direction**: Standard fix is to decrement the target index by one when the target is after the source, before reinserting — e.g. in `reorderSteps`: `const adjusted = fromIndex < clamped ? clamped - 1 : clamped;` then splice at `adjusted`; same idea in `moveToken`'s same-step branch, comparing the dragged token's original index to `index` before removing it. Add a driver check that drags forward (step 1 → after step 2, and a token forward within a step) to lock in the fix.

### Minor

**2. `descriptionFor` helper duplicated verbatim across two components**
- **File/lines**: `src/components/StepDetails/StepDetails.tsx:6-8` and `src/components/TokenDetails/TokenDetails.tsx:14-16`.
- **What I found**: Identical 3-line function (`SAMPLE_TOKENS.find((s) => s.iconId === iconId)?.description`) copy-pasted between the two "details" panels.
- **How I found it**: Grepped `SAMPLE_TOKENS.find` across `src/`; two hits, byte-identical bodies.
- **Consequence**: Low — it's 3 lines and both call sites are simple, so drift risk is minor today. But if the lookup logic ever needs to change (e.g. once icons/descriptions move to a real content pack in Phase 3), there are two places to remember, not one.
- **Severity**: Minor. **Category**: Duplication. **Confidence**: High.
- **Suggested direction**: Move `descriptionFor` into `src/data/sample-tokens.ts` (next to `SAMPLE_TOKENS`/`CATEGORY_LABELS`, which are already shared the same way) and import it from both components.

**3. `TokenCategory` value `"note"` and `InstructionToken.note` share a name but mean different things**
- **File/lines**: `src/model/instruction.ts:11-18` (`TokenCategory` union includes `"note"`) vs. `src/model/instruction.ts:59` (`InstructionToken.note`, a free-text per-token annotation); `src/components/TokenPicker/TokenPicker.tsx:13` still lists `"note"` in `STEP_TOKEN_CATEGORIES`.
- **What I found**: `"note"` as a `TokenCategory` would presumably mean a "sticky note" style token placed in a step, while `InstructionToken.note` is an unrelated user-authored comment field that exists on every token regardless of category. There are currently no sample tokens with `category: "note"` (`src/data/sample-tokens.ts` has none), so `CATEGORIES_WITH_SAMPLES` in `TokenPicker.tsx:15-17` silently filters it out and the category is unreachable in the running app today.
- **How I found it**: Read `model/instruction.ts` fully, then grepped `SAMPLE_TOKENS` for `category: "note"` (no matches) and traced `TokenPicker`'s category-filtering logic.
- **Consequence**: Not a functional bug today (the category simply never renders a tab), but it's a latent naming trap: a future contributor adding a "note" sample token, or grepping for "note" while working on `InstructionToken.note`, is likely to be momentarily confused by the unrelated same-named category.
- **Severity**: Minor. **Category**: Design/Simplification. **Confidence**: High (verified both the type definition and the absence of any note-category sample data).
- **Suggested direction**: Either rename one of the two (e.g. `TokenCategory`'s `"note"` → `"annotation"` or similar) or, if a "note" token category isn't planned soon, drop it from the union and from `STEP_TOKEN_CATEGORIES` until there's real content for it — the type already documents that categories can grow later without other changes.

### Nitpick

**4. `validateDocument` and `migrate` are unused exports**
- **File/lines**: `src/model/validate.ts:28-30` (`validateDocument`); `src/model/migrate.ts:12-23` (`migrate`).
- **What I found**: Neither function has any import site anywhere in `src/`.
- **How I found it**: Grepped `migrate(` and `validateDocument` across `src/` — only their own definitions matched.
- **Consequence**: None currently; both are explicitly documented as stubs for not-yet-started work (`validate.ts`'s comment points to Phase 2 task 14; `migrate.ts`'s comment points to task 19's import system, and `docs/Milestones.md:43,48` confirms both tasks are open). TypeScript's `noUnusedLocals`/`noUnusedParameters` don't flag unused *exports*, so this won't surface in `tsc -b` or `eslint` output — worth knowing only so nobody assumes lint/typecheck would catch an export that quietly stops being needed.
- **Severity**: Nitpick. **Category**: Simplification. **Confidence**: High.
- **Suggested direction**: No action needed now; if task 14/19 slip much further, consider a comment-only reminder or just leave as-is since the rationale is already documented at each definition.
