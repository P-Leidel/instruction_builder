Problem

computeCanvasLayout already knows every chip's exact position, and the drag path throws that away to re-derive it out of rendered markup — twice per drag.

Solution

Convert the pointer's client point into canvas units once via getScreenCTM(), resolve step and slot purely against the CanvasLayout the canvas was rendered from, and commit the slot the preview already established.

A. The seam is in neither interface

data-step-index, data-step-id and data-token-index are the whole contract between the canvas modules and the drag module. Nothing type-checks them; a rename in TokenChip.tsx:125 breaks drag silently.

Three CSS rules are load-bearing on it and say so nowhere: .drag-ghost { pointer-events: none } (global.css:487 — the ghost sits exactly under the pointer, and its comment explains text selection, not hit-testing); the export canvas's width: 0 (global.css:180); and @media print restoring that canvas to width: auto. StepCard emits the drag protocol's attributes unconditionally, so all three mounted canvases publish it — only zero sizing keeps two of them unreachable.

B. The preview and the commit are two resolutions

TokenChip.tsx:134 resolves on every move to draw the marker; :141 resolves again, independently, to perform the move. TokenPicker splits the same way. The preview runs through beginPointerDrag's rAF coalescing; the commit uses raw pointerup coordinates.

Worse, endDrag() at :137 — which calls setDropTarget(null) and setIsDragging(false) — runs before the second resolution. That re-read is correct only because the render it scheduled has not flushed. The rule is written down nowhere, and "the marker said here, the chip landed there" is the whole bug class living in this gap.

C. The testability trap this is an instance of

resolveDropSlot and resolveTokenPointerOutcome are pure and tested. resolveTokenDropTarget and resolveStepDropIndex — the two that read the DOM — have zero unit tests. All three defects fixed in c68c80d (today) lived in that untested caller.

The tested model has already drifted from the real input. The fixture builds every rect exactly CHIP_H tall (pointer-drag.test.ts:64), but data-token-index sits on the wrapping <g>, whose box includes the token-time label drawn at y={-CHIP_TIME_HEADER_HEIGHT + 10}. A timed chip's client rect starts ~14 units higher than an untimed sibling's — and groupIntoRows measures a row's whole vertical span against whichever chip sorted first. Rows are ~98 units apart so it holds today, but the row span depends on which chip happens to have a time attached.

D. Two more symptoms of the same missing seam

canvas-layout.ts's module comment says the geometry primitives are private so nobody re-derives them — then insertionMarkerPosition re-derives two anyway: :349 hand-copies computeRowStartYs' first row, :361 hand-copies chipPosition. The comment above the first one admits the hazard rather than preventing it.

And TokenDropTarget.index is documented "always within [0, tokens.length]", which its consumer does not believe: StepCard.tsx:222 clamps it defensively. Either the invariant holds and the clamp is noise, or it does not and the doc is wrong. A reader cannot tell which.

The sibling function in the same file already does this right: resolveStepDropIndex(clientY, container) takes its container and scopes its query to it. Two resolvers, one file, one job, opposite scoping discipline, no comment on the difference.

Wins
  • Locality: one module owns chip geometry
  • Interface stops being markup and CSS
  • Preview and commit stop disagreeing
  • Whole resolution becomes testable
  • Leverage: keyboard token-move gets slots free
Deletion test

Delete the DOM-scanning half and the attribute contract, the rect building, the elementFromPoint fallback and the three CSS rules that prop it up all vanish into canvas-layout, which already holds the numbers. Complexity concentrates.

Honest cost

TokenPicker is a second drag source with no canvas ref and no layout in scope, so the layout has to be reachable from outside App's render — that is candidate 4, which this depends on. Client rects also survive any CSS transform for free; a CTM conversion has to be shown to. getScreenCTM() does account for transforms and scroll, but that is a claim the driver has to check, not a free property.

Problem

"What happens to the selection when the document changes" is answered in six places with four policies, and nothing tells a seventh mutator which one it needs.

Solution

Repair selection inside setSteps, the funnel every mutator already goes through, and delete the two hand-written copies.

The symptom is live today

repairSelection's own comment is scar tissue from getting this wrong once: a token dragged across steps left selectedStepId stale, so "TokenDetails and StepDetails each ended up reporting 'not selected' for two different, both-wrong reasons." The fix was to call repairSelection from one more site rather than make repair a property of mutation — so the same failure is still reachable one mutator over.

Delete the step that is currently selected while one of its tokens is also selected. removeStepCore:388 reassigns selectedStepId to steps[0] and never clears selectedTokenId. The selectedToken computed then resolves to null, so TokenDetails shows its empty placeholder — while StepDetails reads the stale-but-truthy selectedTokenId directly and drops its selected border. Two panels, two wrong answers, exactly the shape the comment describes. Cosmetic, not data loss — but it is the documented bug, still present.

Correction — the symptom above does not reproduce

Checked before any change was made: removeStepCore:389 does not assign selectedStepId directly, it calls selectStepCore — which sets selectedTokenId to null as well. Deleting the selected step with one of its tokens selected leaves selectedTokenId at null and the selectedToken computed at null; the two panels agree. The finding misread that one line, and with it the claim that this candidate carried a user-reachable symptom.

The restructuring itself still holds on its own terms and shipped on 2026-09-20 — the three hand-written copies are gone and setSteps owns the invariant — but it landed as a structural change with no behaviour change, not as a bug fix. See docs/phase-3/progress/architecture-2026-09-20-selection-repair-funnel.md.

Wins
  • Locality: one place watches selection
  • A seventh mutator inherits it free
  • Deletes logic rather than relocating it
  • Closes a reachable two-panel disagreement
Deletion test

Both hand-written guards are behaviourally subsets of repairSelection on the same input, so folding them in removes code outright. setSteps already exists "so undo/redo history only needs one funnel point to watch" — this is a second invariant that wants the same funnel and does not have it. Complexity concentrates.

Problem

Five mutators hand-write the identical step-then-token traversal, and the copies have already drifted apart.

Solution

One private traversal taking a patch plus its history options; each mutator supplies only what differs.

The drift, concretely

setTokenAttachment checks attachmentsEqual before writing, so re-saving an unchanged Quantity records nothing. setTokenTimeCore — the same token, the same CollapsedField chrome, one field over — has no such check, so opening Token time and pressing Save without changing anything pushes an undo entry and wipes redo. The same behaviour was asked of two copies; only one of them got it.

Confirmed, and wider than stated — implemented 2026-09-20

Unlike candidate 2, this symptom reproduces. Probed at c68c80d before any change, by re-saving a value identical to the one already stored:

Probe past Verdict
Token time, unchanged Save 2 → 3 records an empty undo entry — as stated
Step time, unchanged Save 1 → 2 same bug — not named by this finding
Quantity attachment, re-save 2 → 2 correctly guarded
removeTokenFromStep, unknown token id 0 → 1 records a change that didn't happen

setStepTime sits outside this candidate's token-only scope but carries the identical gap one level up — same DurationField, same form, same symptom. Fixing only the token side would have closed one drift while leaving its twin in place, so it got the comparator too. It guards by hand rather than behind a parallel updateStepIn: the step-level traversal is a single steps.map, and hoisting one line behind an indirection is the move ADR 0002 declines.

The seam shipped as specified, with both properties made unconditional rather than per-field: a patch that changes nothing writes nothing, and a write naming a step or token the document doesn't hold does nothing. ADR 0002's revisit clause fired exactly as written — two call sites needing one comparator — so attachmentsEqual was broadened to fieldValuesEqual and that ADR carries a dated update; the decision against a comparator-taking noopGuard is unchanged. See architecture-2026-09-20-token-write-seam.md.

⚠ Reads near ADR 0002 — but is not it

ADR 0002 declined a shared noopGuard(current, next, isEqual) because the three history guards share a purpose and not a shape — each would still pass the only differing part as a parameter. This is the opposite case: five call sites writing the same shape, which the ADR's own revisit clause sets aside as "ordinary de-duplication, and that is a different question from this one." Nothing here touches reorderStepsCore's index-arithmetic argument, which is what ADR 0002 exists to protect.

Wins
  • Locality: one traversal, one place to fix
  • Guards cannot drift per field again
  • Interface shrinks; implementation absorbs it
  • Pairs with candidate 2 at the same funnel
Deletion test

Delete updateTokenIn and the same five-line nested map reappears in five mutators, each free to forget a guard again. Complexity concentrates.

Problem

The interface says an export can be handed nothing — and does not say that the SVG node and the layout must be the same canvas.

Solution

Build the node and its layout as one value where both are known, and make the field non-nullable past that point.

The pairing nobody enforces

app.tsx:421 passes exportLayout to handleExportPdf; app.tsx:500, eighty lines away, renders the canvas exportSvgRef points at with the same exportLayout. pdf-export.ts:68–70 then slices that node using cardY/height from the other argument. Nothing types, asserts or names the requirement that they match. Pass liveLayout by mistake and every page slices at the wrong offsets — silently, in a downloaded file.

The 2026-09-17 remediation was right to stop scraping those numbers off the DOM, but it traded a coupling that was self-consistent by construction for one that is consistent only by convention. Binding the two into one value gets both properties.

Wins
  • Interface stops lying about its inputs
  • Node and layout cannot be mismatched
  • No export path fails invisibly
  • Three call sites drop a dead case
Deletion test

Delete ExportCanvas and the pairing rule goes back to living in two places eighty lines apart, enforced by a comment. Concentrates — and the nullability half is a narrowing, which passes on locality rather than on the deletion test.

Problem

Two keydown dispatchers map (modifier, key, shift, target kind, suspended) to an action, sealed inside a useEffect that registers a window listener. Nothing can reach the decision.

Solution

Move the branch to lib/ as a pure resolver; leave the listener registration and the dispatch in app.tsx.

This is ADR 0003's own strategy, applied to its last holdout

ADR 0003 declined a DOM test environment and committed instead to: "Where a component holds logic worth testing in isolation, the logic moves out to src/lib/." That move already produced canvas-layout.ts, pointer-drag.ts, quantity.ts and field-placement.ts. app.tsx's keyboard layer is the same shape and never got it.

The behaviour worth pinning is a deliberate asymmetry nothing asserts: undo/redo checks only keyboardShortcutsSuspended(), while copy/paste also checks isTextEntryTarget(event.target) so native text copy is not hijacked. confirmDialogOpen() carries a further twenty-line contract about which call site subscribes App and which does not.

Wins
  • Both input modalities get one shape
  • The text-entry asymmetry gets asserted
  • Interface is the test surface, at last
  • No new dependency, per ADR 0003
Deletion test

Delete the resolver and the branch returns to a window handler where no test can reach it — the same position resolveTokenPointerOutcome was extracted out of, for the same reason. Concentrates.

Same shape, same renderValue={(v) => v.label}. One is a component directory with two files; the other is 37 lines inside its consumer. Nothing says which is right.

Problem

DurationField is shallow — six props in, eight straight out, one element of implementation — and its twin is not a module at all.

Solution

Pick one spelling: either delete DurationField and let both callers use CollapsedField directly, or promote QuantityRow to a module beside it.

Why this is graded Worth exploring and not Strong

The deletion test is symmetric here, which is exactly why the codebase drifted into two answers. Deleting DurationField moves its wiring into two call sites — but QuantityRow is the existence proof that this costs about 37 lines and is already considered acceptable. Promoting QuantityRow instead concentrates nothing but makes the convention legible. Either beats having both.

One tiebreaker for deletion: label exists only to phrase aria-labels, and gets lowercased in two files (CollapsedField.tsx:99, DurationForm.tsx:107) while QuantityForm hardcodes its equivalents — three implementations of one aria-labelling convention.

Two shallow modules in the same cluster, worth folding in

lib/quantity.ts is 18 lines with one export and no test file — while its mirror duration.ts has 129 lines of tests. It was extracted for testability and never tested. Its only caller then re-implements it: QuantityForm.tsx:28 spells out buildQuantity's predicate inline to gate Save, which is precisely the drift DurationForm.tsx:38–43 carries a comment about having already fixed.

validate.ts:45–47's shouldFlagIncompleteStep(step, result) is one line of behaviour behind two parameters, one of which is its own sibling's output on the other. One call site. Tracing why a step shows "!" costs four files for one boolean.

⚠ Adjacent to ADR 0001 — deliberately not reopening it

ADR 0001 kept CollapsedField's dual controlled/uncontrolled mode and set its own revisit trigger: a third or fourth controlled caller with no uncontrolled one. That has not happened, and nothing here argues it should be revisited. CollapsedField is the one genuinely deep module in this cluster and stays as it is.

Top recommendation

Candidate 1 — resolve a drop against the layout

Drag is the hottest code in the repo and the only place three defects shipped together this month, all of them in the one part of the path no unit test can reach. The geometry those defects were about is already computed, already pure and already tested one module away — while the current path derives it twice per drag through markup, with three CSS rules and one unflushed render holding it up. Closing that seam puts "where does a chip sit" in one module and makes the whole resolution testable: the move that already paid off for canvas-layout.ts and field-placement.ts, and the one ADR 0003 commits this project to instead of a DOM test environment.
