Problem: the per-step layouts.map body inlines two distinct modules' worth of behaviour with no seam around either — step chrome (badge/title/remove/reorder, ~130 ln) and token-chip rendering plus its pointer-drag outcome switch (~115 ln) both pass the deletion test: cut either and the same complexity reappears in InstructionCanvas, it doesn't vanish.

Solution: give each region its own module — StepCard (chrome + drag-handle/move wiring) and TokenChip (chip markup, badges, the pointerdown switch) — so InstructionCanvas becomes a thin composition over what computeCanvasLayout already computes.

  • Interface shrinks to step/token props; implementation absorbs the wiring
  • Locality: a chip-badge bug fixes in one module, not a 602-line scroll
  • Leverage: TokenChip becomes testable through its own interface, not the whole canvas
The 2026-09-17 audit this follows up on already named TokenChip as its top recommendation and deferred it. StepCard is new: it only became a comparably-sized inline cluster once step management moved onto the canvas (commit 106e536), after that audit was written — both seams are now overdue, not just one.

Collapse document.ts's four free-text mutators into one field-update module

Worth exploring in-process

src/state/document.ts (lines 440–494, sessionActions 545–569)

Before — 4 adapters, 1 implementation each

updateStepTitleCore — steps.map + coalesce:true
updateStepDescriptionCore — steps.map + coalesce:true
updateTokenLabelCore — steps.map + coalesce:true
updateTokenNoteCore — steps.map + coalesce:true

line-for-line identical shape, four copies

After

updateStepField / updateTokenField

one field-selector param · coalesce intrinsic to the module, not a call-site flag

4 adapters → 1 deep implementation

Problem: updateStepTitleCore, updateStepDescriptionCore, updateTokenLabelCore, updateTokenNoteCore are four separate implementations of the same shape — map over steps (and tokens), replace one field, pass {'{ coalesce: true }'} — differing only in which field and whether it's step- or token-scoped.

Solution: one deep updateStepField/updateTokenField taking a field updater, with free-text coalescing built into that module's interface as an invariant rather than repeated per adapter.

  • One implementation instead of four near-identical clones
  • Locality: the coalescing invariant lives in one place
  • A future free-text field gets coalescing for free, no fifth clone
