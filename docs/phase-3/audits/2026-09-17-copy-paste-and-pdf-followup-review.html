What's already clean — checked and passed

Five areas the 5 new commits touched were checked against the deletion test and found to be well-seamed, not friction. They aren't cards below because there's nothing to deepen:

  • pdf-pagination.ts's paginateSteps is a pure, DOM-free, independently-tested packing function; pdf-export.ts is correctly left holding all the jsPDF/DOM glue. Deleting the split would make the packing algorithm untestable without a real SVG.
  • The token-time/step-size fix in canvas-layout.ts's computeRowStartYs is a single, well-localized, test-covered change — no drift left behind.
  • TokenPicker.tsx's radiogroup is the only tab/radio widget in the codebase — TokenAttachmentPicker was already folded into TokenDetails in an earlier review, so there's no second implementation to reconcile it with. The "stale driver check" it fixed was a test-driver bug (focusing inside a collapsed <details> without opening it first), not a product-code issue.
  • The selected-panel border match (global.css) ties two independent CSS rules to the same --color-accent custom property via a cross-referencing comment — no color literal actually drifted.
  • The icon-library expansion is pure data (27 new token entries) — no architectural surface.

Problem: the per-step layouts.map body still inlines two distinct modules' worth of behaviour with no seam around either. Both pass the deletion test: cut either cluster and its ~115–130 lines reappear somewhere else in InstructionCanvas, they don't vanish.

Solution: give each region its own module — StepCard (chrome + drag-handle/move wiring, lines 304–432) and TokenChip (chip markup, badges, the pointerdown switch, lines 439–553) — so InstructionCanvas becomes a thin composition over what computeCanvasLayout already computes.

  • Interface shrinks to layout/derived props; implementation absorbs the wiring
  • Locality: a chip-badge bug fixes in one module, not a 602-line scroll
  • Leverage: TokenChip becomes testable through its own interface, not the whole canvas
The extraction is cheaper than its two-review-long backlog suggests: every handler either cluster calls (selectStep, moveToken, moveStepUp, …) is already a zero-argument, module-level-bound export of the document session (bindActionsToSession/defaultSession in state/document.ts). A StepCard/TokenChip can import them directly, the same way InstructionCanvas.tsx does today — nothing forces a deep prop-drilled interface. This is a genuinely shallow extraction that keeps getting deferred.

Collapse document.ts's four free-text mutators into one field-update module

Worth exploring carried forward — unchanged by the 5 new commits

src/state/document.ts (lines 450–504, sessionActions 609–610)

Before — 4 adapters, 1 implementation each

updateStepTitleCore — steps.map + coalesce:true
updateStepDescriptionCore — steps.map + coalesce:true
updateTokenLabelCore — steps→tokens.map + coalesce:true
updateTokenNoteCore — steps→tokens.map + coalesce:true

line-for-line identical shape, four copies

After

updateStepField / updateTokenField

one field-selector param · coalesce intrinsic to the module, not a call-site flag

4 adapters → 1 deep implementation

Problem: updateStepTitleCore, updateStepDescriptionCore, updateTokenLabelCore, updateTokenNoteCore are four separate implementations of the same shape — map over steps (and tokens), replace one field, pass {'{ coalesce: true }'} — differing only in which field and whether it's step- or token-scoped. The new copyTokenCore/pasteTokenCore (see below) show the pattern this file uses when a mutator is given its own shape on purpose — these four aren't that, they're accidental repetition.

Solution: one deep updateStepField/updateTokenField taking a field updater, with free-text coalescing built into that module's interface as an invariant rather than repeated per adapter.

  • One implementation instead of four near-identical clones
  • Locality: the coalescing invariant lives in one place
  • A future free-text field gets coalescing for free, no fifth clone

Problem: the same user-visible action — copy a token and confirm it with a toast — is reachable two ways (the Copy button, the Ctrl/Cmd+C shortcut) with its behavior and wording duplicated verbatim across a component file and the app-composition-root file. TokenDetails.tsx's own comment on handleCopy already names app.tsx as sharing its shape — the intent to keep them in sync was there, the seam to do it mechanically wasn't. (Paste doesn't have this problem: both its call sites are a single bare pasteToken() with no toast.)

Solution: extract a shared copyTokenWithToast(step, token) — colocated near the other UI-orchestration helpers in document-actions.ts, or exported from TokenDetails.tsx — that both the button handler and the keyboard shortcut call.

  • Deletion test: if the toast wording or tone changes, or copy gains a side effect (analytics, a different clipboard), two sites need the same edit today
  • Turns a documented intention (the comment) into an actual seam

Top recommendation

Decompose the canvas's per-step render into StepCard and TokenChip modules

This is the third review in a row to carry it forward as the top candidate, and the file hasn't moved a single line since the last one wrote that verdict. The 5 commits since then only strengthen the case: they kept landing new behaviour (copy/paste, PDF pagination, a step-size fix) around InstructionCanvas.tsx without touching it, which is itself a sign the file has become a place people route around rather than into. And the extraction is cheaper than its backlog suggests — every handler either cluster needs is already a module-level-bound export, so StepCard/TokenChip would need no prop-drilled action plumbing, just the per-step/per-token data they already close over. The two new small duplications (candidates 3 and 4) are cheap follow-ups worth doing in the same pass, but neither is where the leverage is.
