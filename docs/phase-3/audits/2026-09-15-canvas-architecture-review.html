The module's own doc comment already claims this is true — "this component only renders whatever that module computes." It isn't, yet: StepLayout carries no chip positions, no connector paths, no horizontal offset. InstructionCanvas.tsx re-derives all three at render time from four separate exported functions plus six raw constants (PADDING, CHIP_WIDTH…), including doing its own centering arithmetic inline (tokensOffsetX) that never lives in canvas-layout.ts at all.

Problem

The interface a caller actually depends on is five functions and six constants, not the one entry point the module advertises — the seam leaks.

Solution

computeCanvasLayout composes chip positions, connector paths, and the offset into each StepLayout; the four helper functions become internal, unexported.

  • Deletion test: delete the module today — the centering math doesn't vanish, it's already sitting in the component. Deepening moves it back in.
  • Locality: a positioning bug has exactly one place to live
  • Leverage: one interface, not five imports to keep straight
  • canvas-layout.test.ts already unit-tests the pieces separately — deepening lets it test the assembled-per-step geometry as one thing, the shape a bug would actually appear in

Problem

One render function carries every visual concern for the whole document. The token chip alone — icon, label, two badge kinds, remove control, drag source, readOnly branching — is ~100 lines nested four levels inside a .map().

Solution

Extract <StepCard> and <TokenChip> as named modules, the same way WarningBadge/QuantityBadge already are — each with a small props interface, not a shared blob of local variables.

  • Deletion test: delete TokenChip today — its ~100 lines don't move anywhere, they're the only copy. Extracting doesn't remove duplication; it buys locality for the one place this complexity already lives.
  • Locality: a chip rendering bug has one file, not a line range inside a 420-line file
  • Leverage: readOnly branching (6 sites today) localizes to the two modules that actually vary by it
  • AI-navigability: a future change to "how a token looks" doesn't require reading step-badge/connector/insertion-marker code to find the right ~15 lines

Problem

The two-stage select rule and the drag-vs-tap decision — real, documented business logic — live only inside a nested onPointerDown closure. The only test surface today is the full Playwright driver.

Solution

Pull the decision (not the DOM wiring) into a small pure function: (wasDrag, isSelected, dropTarget) → Action. The pointerdown handler calls it and dispatches; the function is Vitest-testable with no DOM.

  • Deletion test: delete the function — the branching reappears inline exactly where it was. It concentrates real decision logic, so it earns the seam.
  • Locality: the "which action fires" question has one small function to read, not a render closure
  • Testability: the two-stage-select rule gets a fast unit test alongside state/document.test.ts's existing 38
The 2026-09-14 review deliberately left InstructionCanvas's drag handling out of the shared createClickAfterDragGuard unification, reasoning its click-vs-drag handling is "genuinely different." That's still true and isn't being revisited here — this candidate is narrower: naming the decision function, not merging it with StepList/TokenPicker's.

Top recommendation

Start with deepening canvas-layout.ts

It's the foundation the other two sit on. Once StepLayout carries real chip positions and connector paths, extracting TokenChip means handing it a position, not a chipsPerRow it has to re-derive one from — and the pointerdown decision function reads target/selection state that's already fully computed, not partially assembled at render time. Doing it last would mean touching the same lines twice.
