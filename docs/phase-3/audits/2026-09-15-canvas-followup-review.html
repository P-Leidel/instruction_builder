SvgButton adapter

5 call sites become 5 one-line adapters at the same seam. Enter/Space handling exists once.

Problem

The badge, step-remove, move-up, move-down, and chip-remove controls each carry their own copy of the role/tabindex/onClick/onKeyDown(Enter-or-Space) block — five adapters with no shared interface. They've already drifted: chip-remove calls stopPropagation in both handlers (it sits inside a draggable token), the other four don't need to and don't.

Solution

Give "keyboard-activatable SVG button" one interface — a small SvgButton component or svgButtonProps(onActivate, opts) helper — and have all five sites call it. Deletion test: remove one copy and the block reappears verbatim four more times in the same file — it's earning nothing by staying separate.

Wins

  • Locality: Enter/Space bug fixed in one place, fixed at all five
  • Interface shrinks; implementation absorbs the wrappers
  • Testable once, not re-verified per control
  • ~90 lines of near-duplicate JSX gone

Before

deep modules

StepCard

TokenChip

InstructionCanvas keeps only the layout loop and the two .map() calls; each card/chip becomes its own seam, testable with one step or one token in, markup out.

Problem

The 2026-09-14 review cleared this file at ~400 lines, on the grounds that selection state wasn't duplicated. That argument still holds, but it never claimed the render tree itself was deep — and step management (reorder handle, move up/down, remove, the incomplete flag's offset math) landed afterward, adding a second cluster of concerns to the same tree without changing its shape. At 626 lines, one component now answers for step-card layout, token-chip layout, two independent drag flows, and the two-stage select rule's render-time half.

Solution

Pull StepCard and TokenChip out as their own modules, each taking the slice of a StepLayout/token it needs (already computed by canvas-layout.ts) plus its callbacks. InstructionCanvas keeps the SVG root, the layout memo, and two .map() calls.

Wins if pursued

  • Leverage: step-card and chip logic each get one interface, testable alone
  • Locality: a chip bug can't hide inside step-card code and vice versa
  • Shrinks the file candidate 1 would otherwise leave at ~550 lines
Builds on candidate 1 — extracting SvgButton first removes the boilerplate that would otherwise get copied into both new modules.

The select-vs-drag decision lives inside a pointerdown closure

src/components/InstructionCanvas/InstructionCanvas.tsx · src/lib/pointer-drag.ts

Before

onPointerDown → beginPointerDrag
onMove: set dragGhost, diff+write dropTarget
onDrop: wasDrag ? moveToken : (isSelected ? selectToken : selectStep) ← the rule, inline, untested except via full pointer simulation

deep module

resolveTokenPointerOutcome(wasDrag, isSelected, target)

→ { kind: "select-token" | "select-step" | "move", ... }

A pure function, unit-testable with plain values — no SVG, no pointer events, no Playwright.

Problem

"A quick tap selects; a real drag moves" is a real domain rule (the component's own doc comment names it), but its only home is onDrop's closure. The interface to reach it is "render the canvas, dispatch pointer events, inspect signals" — which is exactly what the Playwright driver does today, and exactly what a unit test can't.

Solution

Extract the decision as a pure function taking wasDrag, current selection, and the resolved drop target, returning what to do. onDrop becomes a thin dispatch over its result.

Wins if pursued

  • The interface is the test surface: a unit test replaces a Playwright-only path
  • Locality: the tap-vs-drag rule has one place to read, one place to change

Narrower than candidate 2 — doesn't require splitting the render tree first, though it reads cleaner once TokenChip owns its own onPointerDown.

Top recommendation

One SVG-button interface, five copies deleted

Smallest cut of the three, no design decisions to grill beyond the interface's own shape, and it's already drifted once (chip-remove's stray double stopPropagation) — evidence the five copies won't stay in sync on their own. It also shrinks the file enough that candidate 2 (splitting StepCard/TokenChip out) starts from a smaller, cleaner base if picked up next.
