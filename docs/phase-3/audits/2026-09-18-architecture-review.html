B. Findings from this pass

Fourteen findings not currently tracked anywhere in docs/. Two were confirmed by running code, not just by reading it; those are marked.

S3 · Medium CONFIRMED BY EXECUTION

4 · Moving a token to an unknown step id silently deletes the token

Files: src/state/document.ts:424–455

Problem: moveTokenCore maps over the steps, filtering the token out of its source step and inserting it into the target. If no step matches toStepId, the removal still happens and the insertion never does. Because changed is set unconditionally whenever the source and target ids differ, the no-op guard doesn't catch it either: the token is deleted, and the deletion is recorded in undo history as a legitimate change.

// Verified against a real DocumentSession:
sessionActions.moveToken(session, stepId, "t1", "no-such-step", 0);
// → steps[0].tokens.length === 0   (the token is gone, not moved)

Reachability: low today — the only caller derives toStepId from a live data-step-id hit test, so the id always exists at drop time. It is graded Medium because the failure mode is silent data loss, and because nothing in the type system or the function prevents a future caller (a keyboard "move token to step" affordance, which is already a tracked gap) from passing a stale id.

Solution: resolve the target step before mutating, and return early if it isn't found — the same shape the function already uses for a missing source token one line above.

S3 · Medium

5 · The PDF export chunk ships ~230 kB of libraries the app never runs

Files: src/lib/pdf-export.ts:68, package.json

Problem: jsPDF 4.2.1's ESM build statically imports html2canvas and dompurify for its .html() API. This app only ever uses the svg2pdf.js path, so neither library is ever executed — but both land in the lazy chunk, and Vite can't tree-shake them out of a pre-minified bundle.

≈ 858 kB raw / ≈ 265 kB gzipped, of which ≈ 230 kB raw / ≈ 59 kB gzipped is dead weight. For comparison the entire app bundle is 106 kB / 31 kB gzipped.

Why it matters now: mobile and tablet testing starts this week, and manual-testing-checklist.md already warns testers that the first PDF export "fetches an extra piece in the background." On a phone on mobile data that pause is a quarter of a megabyte longer than it needs to be, and a failed fetch surfaces as a failed export.

Solution: alias html2canvas and dompurify to an empty stub module in vite.config's resolve.alias. Nothing in this app reaches the code paths that call them, so the stub is never touched at runtime. Verify by re-running the build and checking those two chunks are gone.

S3 · Medium

6 · The Time/Quantity popover positions itself once, horizontally only

Files: src/components/FieldPopover/FieldPopover.tsx:40–78

Problem: three limitations compound. The edge-flip runs inside useEffect(…, []), so it never re-runs on resize or rotation. It only flips horizontally — there is no vertical handling at all, so a popover opened from a trigger low in the viewport renders below the fold. And focus is moved with focus({ preventScroll: true }), which deliberately stops the browser from scrolling it into view. Each decision is individually well-reasoned and documented in the file; together they mean a popover can open where the user cannot see it and the page will not move to help.

Reachability: highest on a phone, where the viewport is short and the on-screen keyboard removes another 40% of it the moment the user taps an amount field. No automated check covers it: the driver measures overflow at 390px with nothing open.

Solution: see candidate 3 — extract the placement decision into a pure function that takes the anchor rect, the popover size and the viewport, and returns a placement. That makes both the vertical case and the re-run-on-resize case testable without a browser, instead of adding more untested branches inline.

S3 · Medium NEEDS A DEVICE TO CONFIRM

9 · Every download revokes its object URL synchronously

Files: src/lib/download.ts:21–28

Problem: downloadBlob creates an object URL, clicks a detached <a download>, and calls URL.revokeObjectURL on the very next line. Chromium tolerates this. Safari — particularly iOS Safari, and particularly for larger blobs like a multi-page PDF — has a long history of cancelling the download when the URL is revoked before the transfer is handed off, and some browsers require the anchor to be in the document at all.

Why it matters now: this is the single code path behind all four export formats, and it has only ever been exercised on desktop Chromium. It is listed as Medium rather than High because it is not yet reproduced — but if iPhone testers report "nothing happens when I export", this is the first place to look.

Solution: append the anchor to document.body before clicking, remove it afterward, and defer the revoke by one turn of the event loop. Three lines, no behaviour change on desktop.

S3 · Medium

13 · An unreadable save is protected for exactly one edit, then destroyed

Files: src/state/persistence.ts:112–141

Problem: when migrate() rejects a saved document, the app falls back to a blank one and tells the user "The old save has not been overwritten." That is true at the moment it is shown, and skipNextAutosave correctly stops the blank document being written immediately. But the very next keystroke autosaves over the unreadable record permanently, with no warning and no way to get it back. The reassuring message and the actual guarantee have different lifetimes.

Solution: before falling back, copy the unreadable record to a second IndexedDB key (…:document.recovered) so it survives regardless of what the user does next, and say so in the toast. Cheap, and it turns "your work is gone" into "your work is recoverable by someone who can read JSON."

S3 · Medium ACCESSIBILITY

7 · The confirm dialogs are modal in behaviour but not in declaration

Files: src/components/ConfirmDialog/ConfirmDialog.tsx:33, src/lib/dialog-focus-trap.ts:32–34

Problem: Import and New-document both carry role="alertdialog" and trap Tab between two buttons, but three things are missing: aria-modal="true" is never set; nothing marks the rest of the page inert or aria-hidden, so a screen reader in browse mode can still walk the document behind the dialog; and when the dialog closes, focus is never returned to the button that opened it, so a keyboard user lands back on <body> and has to Tab from the top. FieldPopover already restores focus correctly — the two dialogs are the ones that don't.

Note: this is pre-existing, not introduced by the ConfirmDialog extraction. The extraction is what makes it cheap to fix, because there is now exactly one place to fix it.

Solution: add aria-modal="true", capture document.activeElement when the trap arms and restore it on teardown (the same pattern FieldPopover uses in its effect cleanup), and set inert on the app root while a dialog is open.

S3 · Medium STRUCTURAL

10 & 11 · The entire component tree has no unit tests, and the browser driver knows only two viewports

Files: src/components/** (1,905 lines, 13 components), .claude/skills/run-instruction-builder/driver.mjs:22,649

Problem: all 155 tests live in lib/, model/ and state/. There is not one test file under src/components/, and no DOM test environment is configured. The only verification any component gets is the browser driver — 56 checks, which is genuinely good coverage — but it runs at exactly two viewport widths, 1400px and 390px. Nothing between them is ever exercised.

The hatched band is the untested region. It contains both sides of the only breakpoint in the stylesheet, and it is exactly where the incoming tablet testers live.

Solution, in two independent parts: (a) add 768px and 1024px passes to the driver — this is cheap, needs no new dependency, and directly de-risks the testing round that is starting now; (b) treat the missing component test surface as an architecture problem rather than a tooling one — see candidate 3. Adding a DOM test environment would mean touching the pinned Vite version, which known-issues.md already defers for good reasons; pushing testable logic out of components does not.

S4 · Low

1 · QuantityForm's Save gate still duplicates buildQuantity's rule

Files: src/components/TokenDetails/QuantityForm.tsx:27–28, src/lib/quantity.ts:16

Problem: the form computes isValid inline and buildQuantity re-derives the identical rule. This is precisely the drift a36b94d just removed from DurationForm, left in place one directory away. They agree today; the fix is a two-line change that makes them unable to disagree.

S4 · Low CONFIRMED BY EXECUTION

2 · buildDuration stores a fractional seconds value whose own label disagrees with it

Files: src/lib/duration.ts:56–69, src/components/DurationField/DurationForm.tsx:23–26

Problem: the d/h/m/s inputs are type="text" and coerced with Number(), so "1.5" is accepted as 1.5. buildDuration clamps the range but never rounds, so it returns a value that contradicts itself:

buildDuration(0, 0, 0, 1.5)
// → { label: "1s", seconds: 1.5 }
//     displayed ↑        ↑ stored, exported, and summed

The fractional part then accumulates through sumDurations into step totals and the document heading, where it stays invisible because formatDuration floors. JSON export round-trips the fractional value; the canvas, the PDF heading and the UI all show the floored one. a36b94d fixed the gate that let a sub-1-second entry through; it did not fix the builder that accepts a fractional one above 1.

Solution: round the total in buildDuration before clamping. One line, and duration.test.ts is already the right place to pin it.

S4 · Low

3 · CollapsedField writes local state even when it is controlled

Files: src/components/CollapsedField/CollapsedField.tsx:71–78

Problem: editing = controlledEditing ?? uncontrolledEditing, but setEditing unconditionally writes uncontrolledEditing as well as calling onEditingChange. The component therefore holds two sources of truth and relies on an unstated invariant: that a controlled caller passes a non-undefined boolean on every render. Both current controlled callers do. The moment one passes editing conditionally, the stale local value takes over and the field opens or closes on its own.

Note: this is the candidate flagged in the previous architecture report as having "the strongest deletion-test evidence on the list (two independently shipped bugs)". It is still open, and this pass confirms the invariant is still unenforced.

Solution: only write local state when controlledEditing === undefined. Or, better, split the decision out of the component entirely — see candidate 3.

S4 · Low ACCESSIBILITY

8 · FieldPopover traps Tab while declaring itself non-modal

Files: src/components/FieldPopover/FieldPopover.tsx:80–98,101

Problem: the element is role="dialog" aria-modal="false", which tells assistive technology "you can move out of this normally" — and then the keydown handler cycles Tab back to the first control, so you cannot. A keyboard user's only exits are Escape, Save, or Cancel. Either declaration would be defensible; the contradiction is what isn't.

Solution: decide which it is. Given this popover edits a value and has an explicit Cancel, modal is the honest answer: set aria-modal="true" and keep the trap.

S4 · Low

12 · migrate() passes unknown properties straight through into the saved document

Files: src/model/migrate.ts:135

Problem: the final return { ...doc, steps } as unknown as InstructionDocument keeps every property the input JSON carried, validated or not, and the same applies per step and per token. An imported file can therefore inject arbitrary keys that are then autosaved and re-exported forever. There are also no length bounds: the UI caps titles at 50 characters and notes at 249, but an imported document is not checked against either, so a 10,000-character title renders straight into the toolbar input and the confirm dialog.

Reachability and impact: low — this is a local-first app with no server and no rendering of raw HTML, so the exposure is bloat and layout damage, not injection. Worth folding into Phase 4 task 32 rather than fixing in isolation.

Solution: construct the returned document from named fields instead of spreading, and clamp imported string lengths to the same constants the UI enforces.

S4 · Low

14 · A single step taller than one PDF page overflows the page margins

Files: src/lib/pdf-export.ts:90–113

Problem: paginateSteps deliberately places an over-tall step alone on its page rather than splitting it — correct. But pdf-export then renders that slice at sliceHeight * scale, which for such a step exceeds the usable page height, so it runs off the bottom of the A4 page instead of being scaled down to fit. The existing comment estimates this needs roughly 70+ tokens in one step.

Solution: when a page holds exactly one step and its scaled height exceeds USABLE_HEIGHT_MM, derive the scale from the height instead of the width and centre the result horizontally.

D. Architecture candidates

Deepening opportunities, in the vocabulary of /codebase-design: a module is deep when a lot of behaviour sits behind a small interface, and a seam is where that interface lives. Each candidate is judged by the deletion test — would removing it concentrate complexity, or just move it?

Strong TOP RECOMMENDATION

Candidate 3 · Give field placement and field open/close state a real seam outside the components

Files: src/components/FieldPopover/FieldPopover.tsx, src/components/CollapsedField/CollapsedField.tsx, src/components/TokenDetails/TokenDetails.tsx (TimeAndQuantityRow)

Problem: two pieces of real decision logic are trapped inside render functions where nothing can test them. FieldPopover decides where a popover goes — currently one horizontal comparison, run once at mount, with no vertical case. CollapsedField decides whether a field is open — currently two overlapping state sources held together by an unwritten rule. Both are pure functions wearing component costumes. The consequences are already visible: findings 3 and 6 are both symptoms of the same missing seam, and the placement bug is the single most likely thing mobile testers will hit this week.

Solution: extract two small pure modules into lib/ — the same move that already paid off for canvas-layout.ts and pointer-drag.ts.

  • resolveFieldPlacement(anchorRect, popoverSize, viewport) → { horizontal: "left" | "right", vertical: "below" | "above" }. Pure arithmetic, no DOM. The component's effect becomes: measure, call, apply — and re-run on resize, because now that is one extra dependency rather than one more untested branch.
  • resolveFieldEditing(controlled, local), or simply the discipline that local state is only written when controlled === undefined. Small enough that the honest version is a guard clause, not a module.

Deletion test: delete field-placement.ts and the vertical-flip rule, the edge-flip rule and the resize rule scatter back into every component that floats something. Complexity concentrates — it earns its keep.

Speculative — recommend NOT doing

Candidate 1 · Consolidating the three no-op guards

Files: src/state/document.ts:256, 269, 442, 483

This was raised as an open question after the last review and deserves a straight answer, so it is included here as a candidate that should be closed, not built.

The case for: three checks — tokensEqual, clamped === fromIndex, attachmentsEqual — were added in one commit, all serving one concept: "don't record history for a change that changed nothing." Three differently-named helpers for one idea looks like Duplicated Code.

The case against, which is stronger: they only share a purpose, not a shape. One is per-slot identity over an array whose elements are provably never cloned. One is index arithmetic that is a proof of equality, not a comparison — reinserting at the removal index reconstructs the original exactly, which is cheaper and more precise than comparing arrays. One is shallow key/value equality over a flat object. A shared noopGuard(current, next, isEqual) would take the comparator as a parameter, meaning each call site still supplies the only part that differs, while the shared part collapses to if (isEqual(a, b)) return; — a single line, hoisted behind an indirection, for one caller each. That is textbook Speculative Generality.

And there is a specific thing to lose: reorderStepsCore's comment argues that the index check is "a precise stand-in for a full array-value-equality check, not just an approximation of one." Generalising it into a comparator parameter is exactly how that reasoning gets deleted, and how the next person "simplifies" it into a slower array comparison believing they are fixing an approximation.

What is worth doing instead — a five-minute version: nothing structural. Add one sentence to setSteps's doc comment naming the convention ("callers that can cheaply detect a no-op guard before calling this, so history is not polluted; see the three guards below, deliberately different in shape"). The concept becomes visible without an abstraction existing to hold it.

Deletion test result: deleting a hypothetical shared guard would move one line to three places, not concentrate anything. It fails the test, which is why this is the recommendation to decline.

Worth exploring

Candidate 4 · Stop letting a null SVG node mean "export silently did nothing"

Files: src/lib/document-actions.ts:80–101, src/app.tsx:90–114

Problem: 76f17fb replaced a class-name querySelector with a typed ref — a real improvement — but kept svgElement: SVGSVGElement | null in CanvasExportInput. So the nullability propagates into every export entry point, and runCanvasExport handles it by returning {}: no file, no error, no toast. The user clicks Export and nothing at all happens. The code comment argues this is unreachable after first render, which is probably true — and if it is true, the type should say so rather than forcing three call sites to carry a case that cannot occur.

Solution: have App narrow once at the click handler, and make CanvasExportInput.svgElement non-nullable. If the ref really is null, that is a genuine error worth a toast, not a silent return.

Benefits: the interface stops lying about what can happen, and the one remaining path where an export can do nothing visible is removed just as mobile testers — who have the least ability to diagnose a silent failure — start exercising it.

Worth exploring

Candidate 5 · Move canvas layout behind a computed signal instead of App's render

Files: src/app.tsx:310–321, src/lib/canvas-layout.ts

Problem: App reads document.value.steps in its own body purely to feed two useMemo calls. That subscription makes the whole application root re-render on every keystroke, which is the opposite of what a signals architecture is for — and state/document.ts already demonstrates the right pattern with selectedStep/selectedToken as computed().

graph LR subgraph Now D1[document signal] --> A1[App render] A1 --> M1["useMemo liveLayout"] A1 --> M2["useMemo exportLayout"] M1 --> C1[live canvas] M2 --> C2[preview canvas] M2 --> C3[hidden export canvas] end subgraph Proposed D2[document signal] --> K1["computed exportLayout"] D2 --> K2["computed liveLayout"] K1 --> P2[preview canvas] K1 --> P3[hidden export canvas] K2 --> P1[live canvas] A2[App render] -.->|no document subscription| P1 end

Benefits: locality — "what is the current layout?" becomes one derived value with one definition, rather than two memos hanging off a component's render. Leverage — anything else that needs the layout (a future radial renderer, per planned-additions.md item 2) reads the signal instead of being handed a prop from the root.

Honest limit: this does not fix the known per-step re-render issue, which known-issues.md correctly traces to computeCanvasLayout recomputing every cardY from scratch. It fixes the cheaper, separate problem of the application root re-rendering for no reason. Worth doing on its own terms; worth not overselling.

Speculative

Candidate 2 · Splitting state/document.ts

Files: src/state/document.ts (782 lines — the largest file in the project)

The observation: one file holds session construction, the undo/redo history engine with its coalescing clock, selection repair, and twenty-five mutators. On size alone it looks like a split candidate.

Why it is only speculative: the module is already deep in the sense that matters. Its interface is a set of zero-argument verbs plus one createDocumentSession() factory; history is already funnelled through a single setSteps, so there is exactly one place to watch. Splitting the history engine out would create a new seam that nothing varies across — one adapter, hypothetical, not real. Much of the 782 lines is doc comments recording why each decision was made, which is the opposite of the problem a split solves.

Revisit if: a second document session ever needs a different history policy (a bounded-size one, or no history at all). That would be the second adapter that makes the seam real.
