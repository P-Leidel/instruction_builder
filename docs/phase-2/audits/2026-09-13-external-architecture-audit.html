1 · Make the document session constructable

Strong in-process

src/state/document.ts · src/state/persistence.ts · tests/ (empty) · .claude/skills/run-instruction-builder/driver.mjs · .github/workflows/ci.yml

Before — the test surface is the browser

After — the interface is the test surface

Problem Every document rule — 24 mutators, snapshot history, the 700 ms coalesce window — is pure in-process computation, but it is bound to module-level singletons plus module-level lastPushWasCoalesce / lastPushAt and Date.now(), so nothing can construct a second document and the interface can only be exercised through a live browser.

Solution Make the document session something you create, with its state, history and clock handed in; keep the module-level signals as one thin adapter over it so no caller changes today.

Deletion test

Delete the singletons and complexity concentrates — one session module owns history, coalescing and selection repair. It does not move: today that complexity is already spread across document.ts, persistence.ts and the canvas's two-stage selection rule.

Wins

  • leverage: one interface, 24 mutators
  • coalescing testable without typing
  • tests run in CI, not in Chromium
  • locality: selection repair in one module
  • opens Phase 2 task 20
  • ends the window.document shadowing
Also under this seam: restoreDocument re-stamps meta.updatedAt, so undo is not a pure inverse — a fact no caller can learn from the interface.

Callers say what is being dragged. The module says where it lands.

Problem “Drop-before index in the pre-removal array” is a fact a caller must know, and it is spread across four modules: two resolvers with different algorithms, one in lib/ and one private inside a component, plus two consumers that each re-derive the same forward-move adjustment. The same off-by-one shipped in both consumers. DropTarget and TokenDropTarget are duplicate types with the same comment copied verbatim, and justDragged is a module-level flag declared twice.

Solution One module owns the whole gesture — ghost, drop resolution, click suppression, commit — so a caller names the thing being dragged and nothing else; the index convention stops being public.

Deletion test

Delete beginPointerDrag alone and complexity merely moves — each call site grows its own listeners. Delete it and absorb the six-step protocol its three call sites repeat, and complexity concentrates: one place where an index convention can be wrong.

Wins

  • locality: one off-by-one, not two
  • interface shrinks; implementation absorbs it
  • drop resolution testable as arithmetic
  • drops two duplicate types
  • drops the duplicated suppression flag
  • step reorder can gain an insertion marker

3 · Lift the canvas layout out of the component

Strong in-process top pick

src/components/InstructionCanvas/InstructionCanvas.tsx:18–268 (geometry) · :323–591 (render) · src/lib/pointer-drag.ts:84–102

Before — geometry sealed inside the render

After — one layout module, three consumers

Problem About 250 of the canvas's 591 lines — 42% — are pure geometry with no framework in them, and none of it is exported. buildConnectors emits 40 lines of exact SVG path strings verifiable only by eye. The component computes each chip's position and then recovers that same position from the DOM through elementFromPoint and data-* attributes.

Solution Move the geometry into its own module — document and width in, positioned geometry out. The canvas renders it, hit-testing queries it instead of the DOM, and the export pipeline renders from it instead of scraping markup.

Deletion test

Delete the layout module and its geometry reappears in three places — the canvas, the hit-test, and the export renderer. It is earning its keep before it exists.

Wins

  • connector paths testable as strings
  • the full-row append edge case pinned down
  • export stops scraping rendered DOM
  • hit-test stops round-tripping the DOM
  • leverage: one layout, three consumers
  • canvas drops to roughly render-only
Supported by the project's own note — docs/Planned-Additions.md #2 says to watch for “code outside InstructionCanvas (e.g. the export pipeline, tasks 15–17) that assumes there is exactly one canvas layout shape, rather than treating layout as a pluggable renderer.” Task 15 is next. No ADR exists to conflict with.

Two adapters — a file and a store — justify the seam.

Problem A document enters the app two ways with different rules. The file path parses, migrates, validates, stages and confirms across four modules with no single entry point. The IndexedDB path casts the stored record straight into the signal, never calls migrate, and on a version mismatch discards the saved document — which the save effect then overwrites with the empty default about 200 ms later.

Solution One intake module both sources go through, so migration, shape checking and the replace decision are stated once and the store is just another source.

Deletion test

Delete it and the four-step sequence reappears at both call sites — which is exactly the state today, and exactly why one of them is missing a step.

Wins

  • locality: one place a version is judged
  • closes a silent data-loss path
  • round-trip testable against a fake store
  • selection repair after load stops being a caller rule
Live defect, independent of whether this deepening is taken: a saved document whose schemaVersion does not match is dropped and then overwritten, with no prompt. migrate() already handles this case; the load path just never calls it.

Problem The token category and attachment vocabulary is enumerated in seven modules, two of them hand-maintained copies that already disagree on ordering. A quantity's amount and unit are fused into a display string at the point of entry, and a duration's label is precomputed and persisted next to its seconds, so the model carries derived state that nothing reconciles.

Solution One module owns what an attachment is — the kinds, their order, how one is built from input and how it is shown — so the picker, the canvas badges and the details list all read the same source.

Deletion test

Weaker than the candidates above: delete it and the complexity mostly moves back into three render sites rather than vanishing. It earns its keep at Phase 3, when content packs supply the vocabulary as data — at which point seven enumerations become seven migration sites.

Wins

  • locality: one vocabulary, one order
  • quantity stays editable after attaching
  • derived labels stop being persisted
  • Phase 3 content packs get one seam

Top recommendation

Lift the canvas layout out of the component

Task 15 is next, and it is the task that decides where this seam goes. Built against the component as it stands, the export pipeline serializes rendered DOM and the layout is locked inside the canvas for good. Built against a layout module, the same geometry serves the canvas, the hit-test and the export — and the radial layout the project already wrote down becomes a second adapter rather than a second canvas.

It is also the cheapest first test target in the repo: roughly 250 lines that are already pure and already framework-free. Candidate 1 is the deeper win and should follow it — but it touches every component, and nothing needs to wait for it.

Independent of all of this: candidate 4 describes a live data-loss path on load. Worth closing on its own, now.
