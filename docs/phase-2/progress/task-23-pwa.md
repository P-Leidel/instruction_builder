# Task 23 — Convert to PWA

> 📌 **Doc status: CURRENT** — one file in the
> [Phase 2 Progress Log](./README.md).

The plan's scope: "Enable installation and offline operation on Vercel;
keep Vite's `base`, manifest, and service-worker scope aligned to the
Vercel domain root." Phase 1 deliberately left groundwork for exactly this
(`public/manifest.webmanifest` with an empty `icons` array, an empty
`public/icons/` folder, `vite.config.ts`'s `base: "/"` - see
[phase-1/foundation.md](../../phase-1/foundation.md#pwa-groundwork)) and
explicitly deferred the rest - the service worker itself, app icons, and
wiring registration up - to this task, "so that task doesn't require
restructuring anything."

## Scoping decisions (made with the user before starting)

Two open questions, asked before writing any code:

1. **Service worker implementation: hand-written, no new dependency** -
   over `vite-plugin-pwa`/Workbox. Matches the minimal-dependency principle
   `foundation.md` already committed to for this exact groundwork. The
   tradeoff, accepted going in: a runtime-only cache (assets are cached as
   they're requested, not precached as a build-time manifest), so the very
   first-ever visit to any given asset still needs the network - offline
   support starts working from the second visit onward, not the first.
2. **App icon: generated from an existing Lucide icon** (`clipboard-list`,
   already in the same icon language this app uses for tokens - see
   `src/data/icon-library.ts`) rendered on a solid accent-color square,
   rather than a bespoke logo. Kept the whole app's icon language
   consistent with zero new asset dependencies.

## What was built

- **`public/icons/`** - `icon-192.png` and `icon-512.png` (`purpose: "any"`),
  `icon-maskable-512.png` (icon content scaled to 60% and centered, so it
  survives an OS's circular/square mask crop), and `favicon.svg` (the same
  design, but full-bleed with no maskable-safe-zone shrinking - favicons
  aren't cropped by an OS mask the way a maskable home-screen icon is).
  Generated by rendering inline SVG through a real browser (Playwright,
  already a devDependency for the driver) at each exact pixel size, rather
  than adding an image-processing dependency for a one-time task.
- **`public/manifest.webmanifest`** - its previously-empty `icons` array
  filled in with the three PNGs above.
- **`index.html`** - a linked favicon (`<link rel="icon">`, none existed
  before this task at all), plus `apple-touch-icon`/`apple-mobile-web-app-*`
  tags - iOS's home-screen install doesn't read the manifest's `icons`/`display`
  the way other platforms do, so it needs this separate, older route to the
  same result.
- **`public/sw.js`** - a hand-written service worker (see "Scoping
  decisions" above): `install` calls `skipWaiting()` and `activate` deletes
  any cache not matching the current `CACHE_NAME` before calling
  `clients.claim()`, so an updated deploy takes over promptly instead of
  needing every open tab closed first. Its `fetch` handler only ever
  touches same-origin `GET` requests: navigations (loading/reloading the
  page) are network-first with a cached-shell fallback, so an online user
  always gets the current build; everything else (hashed JS/CSS bundles,
  the manifest, the icons) is cache-first, since a hashed filename never
  changes meaning once built.
- **`src/main.tsx`** - registers `/sw.js`, gated behind
  `import.meta.env.PROD` so `npm run dev` (and this project's Playwright
  driver, which drives the dev server) is completely unaffected -
  registering a caching service worker against Vite's own fast-refreshing,
  unhashed dev modules would actively fight with HMR.
- **`eslint.config.js`** - a scoped override so `public/sw.js` lints with
  service-worker globals (`self`, `caches`, `clients`) instead of browser
  globals, the same way `.claude/` gets its own tooling-script treatment,
  except `sw.js` is real shipped code, so it's linted, not ignored.

## Bugs found and fixed before this ever shipped

Two real defects, both in `sw.js`, both caught by actually testing against
a production build rather than trusting the code by inspection - see their
own Fixed Issues entries for full root-cause detail:

1. [A naive service worker fetch handler broke every page reload](../../fixed-issues/service-worker-broke-every-page-reload.md) -
   a reload's navigation request can carry `cache: "only-if-cached"` paired
   with `mode: "navigate"`, and re-fetching that exact `Request` object
   throws immediately.
2. [The service worker's runtime cache silently cached nothing, ever](../../fixed-issues/service-worker-never-actually-cached-anything.md) -
   `response.clone()` was called too late (inside an already-async chain),
   throwing silently once the page had started reading the original
   response's body.

Both were only caught because verification here specifically included
reading `caches.open(...).keys()` back after a load and then actually going
offline and reloading - a superficial check (does the service worker
register? does a reload still work online?) would have passed the whole
time despite offline support not existing yet.

## Verification

`npm run lint`, `npm run typecheck`, `npm test` (107 tests, unaffected -
this task touched no model/state logic), and `npm run build` all pass. A
new script, `.claude/skills/run-instruction-builder/pwa-check.mjs`, checks
what `driver.mjs` structurally can't (it drives the dev server, where the
service worker is deliberately never registered - see above): run against
a real `npm run build && npm run preview` output, it confirms the manifest
and all three icons are reachable, that the service worker actually
controls the page, that a simulated "second visit" populates the runtime
cache with the page shell and its hashed assets, and - the actual point of
this task - that the app still loads and renders with the browser context
fully offline. All pass, with zero failed requests.
