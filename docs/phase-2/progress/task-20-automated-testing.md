# Task 20 — Add Automated Testing

> 📌 **Doc status: CURRENT** — one file in the
> [Phase 2 Progress Log](./README.md).

- Planned first in [../plans/task-20-automated-testing-plan.md](../plans/task-20-automated-testing-plan.md), written after (and explicitly informed by) `docs/known-issues.md` and `docs/planned-additions.md`, before any Task 20 code existed. The plan's central call: unit tests **complement** the existing Playwright driver rather than re-covering it - almost every interactive flow already has real-browser, end-to-end coverage, so Vitest's job here is fast, in-process, edge-case coverage of pure logic the driver can't practically reach one branch at a time (the coalescing window's exact boundary, every individual `migrate` rejection reason, `adjustIndexForRemoval`'s off-by-one cases).
- **Decision, with explicit sign-off:** the only `vitest` versions compatible with the pinned `vite@^5.4.11` (2.x-4.x) all depend on a critical-severity `@vitest/mocker` advisory (UI-server-only, a mode this project never invokes). Accepted rather than forcing a Vite major upgrade first, matching the precedent already set for the existing vite/esbuild dev-only entries in `known-issues.md` - see that doc's "`vite`/`esbuild`/`vitest` dev-only vulnerabilities" entry.
- `vitest@2.1.9` added as a devDependency, with a standalone `vitest.config.ts` (`environment: "node"`, `include: ["src/**/*.test.ts"]`) rather than merging into `vite.config.ts` - nothing in scope needs JSX or the Preact plugin. `package.json` gained a `"test": "vitest run"` script (one-shot, matching `lint`/`typecheck`/`build`'s style, not watch mode). `tsconfig.node.json`'s `include` gained `vitest.config.ts` alongside the existing `vite.config.ts`.
- 107 tests across 8 colocated `*.test.ts` files:
  - `model/instruction.test.ts`, `model/migrate.test.ts`, `model/validate.test.ts` - document/step/token creation defaults, every one of `migrate`'s individual shape-rejection reasons, and `validateStep`/`validateDocument`'s completeness rules.
  - `model/migrate.test.ts` also carries a regression test for the still-open known-issues.md item ("token/attachment vocabulary enumerated in seven places, two of them already disagreeing"): a `Record<TokenCategory, true>` literal, independent of `migrate.ts`'s own internal `TOKEN_CATEGORIES` array, forces a compile error if `TokenCategory` ever gains/loses a member without this test being updated to match - then a table-driven test asserts `migrate` accepts a token of every one of those categories, so a drift between the type and `TOKEN_CATEGORIES` fails a real test, not just a compile check. Confirmed to actually catch it by temporarily dropping `"time"` from `TOKEN_CATEGORIES` and watching the test fail, then restoring it.
  - `state/document.test.ts` (31 tests) - the centerpiece, exercising `sessionActions` via `createDocumentSession()`: two independent sessions never share state; every mutator (add/remove/move/reorder/attach/time); `moveTokenCore`/`reorderStepsCore`'s shared `adjustIndexForRemoval` at its boundary cases - forward move, backward move (no adjustment needed), drop to index 0, and drop past the end (append) - covered for both `moveToken` (within a step) and `reorderSteps`; undo/redo including the `MAX_HISTORY` cap and a new-action clearing the redo stack; coalescing (via `vi.useFakeTimers()` rather than real waits) both merging within the window and starting fresh once it passes or a non-coalescing action intervenes; and `restoreDocument`'s selection-repair on undo/redo, both "selection stays put" and "selection falls back/clears" branches. Confirmed several of these actually catch a regression, not just pass vacuously, by temporarily breaking `COALESCE_WINDOW_MS` and `adjustIndexForRemoval` in turn and watching the relevant tests fail, then restoring both.
  - `lib/canvas-layout.test.ts`, `lib/duration.test.ts` - pure geometry and duration math. Connector-line tests check the `d` path's start/end coordinates and curve-vs-straight shape rather than asserting an exact full path string, so they don't need updating every time the drawing constants (`CHIP_GAP`, `CONNECTOR_LEAD_OUT`, etc.) get tuned, as they already have twice in this project's history.
  - `lib/document-file.test.ts` - `slugify` (including today's actual `"untitled-instructions"` fallback, asserted as current behavior per the still-open filename item in `known-issues.md`, not routed around) and `parseImportedDocument`.
  - `lib/pointer-drag.test.ts` - `createClickAfterDragGuard`'s mark/check/reset behavior and per-instance independence.
- Deliberately **out of scope**, left to the Playwright driver: `lib/svg-export.ts`/`png-export.ts`/`pdf-export.ts` (real computed-style baking, canvas rasterization, and `window.print()` - jsdom/happy-dom's incomplete CSS support risks false confidence or false failures either way, and the driver already checks the real thing in real Chromium), `state/persistence.ts` (real IndexedDB timing, including the accepted 200ms-window known issue - a unit test would either have to fake IndexedDB unfaithfully or assert around a real, accepted limitation), `lib/pointer-drag.ts`'s `beginPointerDrag`/`resolveTokenDropTarget` (real Pointer Events/`elementFromPoint` hit-testing), and every Preact component (would need `@testing-library/preact` plus a DOM environment - a bigger step the plan's wording doesn't ask for).
- `.github/workflows/ci.yml` gained a `npm test` step, between `typecheck` and `build` - satisfies the plan's explicit "run in CI" requirement.
- `run-instruction-builder`'s `SKILL.md` extended (frontmatter description and the "Build" section) to run `npm test` alongside `lint`/`typecheck`/`build`, rather than creating a separate skill - no new command existed to document before this task, and a parallel skill would have duplicated the existing one's Prerequisites/Gotchas for no benefit.
