## Findings

### Minor

**1. `QuantityForm`'s draft input persists across token selection changes**
- **File/lines**: `src/components/TokenAttachmentPicker/TokenAttachmentPicker.tsx:20-65` (`QuantityForm`, local `useState` for `amountText`/`unit`); rendered from `:106` with no `key`; the parent `<TokenAttachmentPicker />` itself is also rendered with no `key` in `src/app.tsx:63`.
- **What I found**: `QuantityForm` keeps `amountText`/`unit` in local component state with no reset tied to which token is currently selected (`selectedToken.value` from `state/document.ts`). Since Preact keeps the same component instance mounted across re-renders at the same tree position, switching the selected token (clicking a different token on the canvas) does not clear a partially-typed or previously-attached amount/unit — the form silently carries it over to whatever token is selected next.
- **How I found it**: Read `TokenAttachmentPicker.tsx` in full, noticed `QuantityForm` has no `key` prop and no `useEffect`/derived-state reset keyed on `selectedToken.value.id`, then cross-checked against `docs/Fixed-Issues.md`'s "DurationField showed a stale, unsaved edit after switching tokens or steps" entry — the exact same root cause (`no key -> Preact reuses the instance -> local state leaks across a selection change`) that was already found and fixed for `DurationField` in `StepDetails.tsx:53-58`/`TokenDetails.tsx:72-77` via `key={step.id}`/`key={token.id}`, but the same treatment wasn't applied here.
- **Consequence**: Lower severity than the `DurationField` bug because `QuantityForm` never *displays* an existing value as if it belonged to the new token — there's no attached-quantity readout to get wrong. But it does mean: type "250" intending to attach it to token A, select a different token B before clicking Attach, and the "250" is still sitting in the form for B — a moment's inattention attaches the wrong amount to the wrong token, with no visual cue that the value is stale. This is plausibly an intentional convenience (repeating the same quantity for several consecutive tokens without retyping) rather than an oversight, but nothing in the code or docs indicates it was a deliberate choice, unlike every other stateful-panel decision in this codebase, which is otherwise commented.
- **Severity**: Minor. **Category**: Correctness / Design. **Confidence**: Medium (the mechanism is verified; whether it's an oversight vs. deliberate convenience is not).
- **Suggested direction**: If unintentional, add `key={token.id}` on `QuantityForm`'s usage (mirroring the `DurationField` fix) so switching tokens resets the draft to `("1", EU_FOOD_UNITS[0].value)`. If the carry-over is actually wanted (fast repeated attachment of the same quantity to several tokens), a one-line comment saying so would keep this from looking like the same bug class the project already fixed once this session.
